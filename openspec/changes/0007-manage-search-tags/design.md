# Design

## Context

见 `proposal.md`。搜索与标签逻辑大部分是纯数据计算，放在 `BizScanCore` 可在本机验证；UI 只负责输入与展示。

## Goals / Non-Goals

**Goals:**

- 搜索不依赖数据库查询能力，内存过滤即可覆盖当前规模。
- 标签唯一性大小写不敏感，删除标签不删除名片。
- 删除名片必须同时删除图像，避免磁盘泄漏。

**Non-Goals:**

- 不做全文索引或分页。
- 不做标签颜色、排序、层级。
- 不做批量删除。

## Decisions

1. **搜索在内存中执行（`SearchQuery` 过滤已加载列表）**
   - 理由：名片规模在几十到几百，内存过滤足够；纯函数易测试。
   - 备选：SwiftData `#Predicate` 查询（被否：多字段模糊匹配表达受限，号码格式归一化困难）。

2. **号码搜索比较"数字键"而非原字符串**
   - 理由：用户可能输入 `1380000` 而名片存 `+86 138 0000 0000`。
   - 备选：仅子串匹配（被否：格式差异导致漏检）。

3. **标签独立建表，名片只存标签名**
   - 理由：筛选栏需要全局标签集合；删除标签需要批量从名片移除。
   - 备选：从名片数组反推（被否：删除/重命名后残留）。

4. **删除名片时先删图像再删记录**
   - 理由：与保存顺序相反，保证不会出现"记录消失但文件残留"的可见问题；文件删除失败不阻断记录删除。
   - 备选：仅删记录（被否：磁盘泄漏）。

## Risks / Trade-offs

- [内存过滤在名片极多时变慢] → 当前规模可接受；记录为一般风险。
- [标签删除不可撤销] → UI 二次确认由后续 change 决定；当前仅删除标签本身，不删除名片。
- [搜索命中字段高亮尚未实现] → `matchedFields` 已返回命中字段，UI 暂未高亮；登记为待办。

## Migration Plan

无 schema 变更。`TagEntity` 在 `0001` 已创建。

## Open Questions

- 是否需要"仅搜索已选标签范围"？当前搜索与标签筛选互斥（搜索页独立），可在后续按需扩展。
