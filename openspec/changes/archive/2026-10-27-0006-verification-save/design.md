# Design

## Context

见 `proposal.md`。校正页同时承担"展示 AI 结果"和"生成可靠数据"两个职责，必须让用户看清哪些字段来自识别、哪些是待定内容，并允许全部修改。

## Goals / Non-Goals

**Goals:**

- 保存前不写任何持久化存储。
- 一次保存最多产生一条记录，且图像与记录引用一致。
- 空字段保存时给出提示但不阻断（由用户明确确认）。

**Non-Goals:**

- 不做字段级撤销/重做栈。
- 不做自动保存草稿（中断即丢弃，符合 `verification` 规范）。

## Decisions

1. **编辑态使用 `String` / 多行文本，保存时再拆分为数组**
   - 理由：SwiftUI `TextField` 直接绑定字符串最简单；拆分规则集中在 `splitLines`。
   - 备选：逐项编辑数组（被否：多值增删 UI 复杂，当前收益低）。

2. **保存顺序：先写图像，再写数据库**
   - 理由：记录存在但图像缺失会导致详情页空白；先写图像可在数据库失败时留下可清理的孤儿文件。
   - 备选：先写数据库（被否：详情页会短暂引用不存在的图像）。
   - 待改进：数据库失败时未回滚已写图像，已登记为一般风险。

3. **用 `isSaving` 幂等保护**
   - 理由：防止连点产生重复记录（`verification` 场景）。
   - 备选：按钮防抖（被否：不能覆盖快速两次点击的竞态）。

4. **空名片二次确认**
   - 理由：允许用户保存只有图像的名片，但必须显式确认。
   - 备选：直接禁止保存（被否：部分名片确实无可用文本）。

5. **标签在保存时一并创建**
   - 理由：`TagEntity` 与名片同事务，避免标签筛选栏缺项。
   - 备选：先建标签再保存名片（被否：中断会产生无主标签）。

## Risks / Trade-offs

- [数据库保存失败后图像成为孤儿文件] → 记录到 `docs/verification-debt.md`；后续可增加清理任务。
- [编辑态字符串拆分可能误切含逗号的地址] → 地址不参与 `splitLines`（仅电话/邮箱使用），已按字段区分。
- [详情页编辑后列表排序变化可能让用户"丢失"名片] → 列表按 `updatedAt` 倒序，符合 `card-model` 规范。

## Migration Plan

新增字段均来自既有 schema，无迁移。若后续增加 OCR 原文持久化，需新增实体并提供默认值。

## Open Questions

- OCR 原始文本是否入库？当前仅在内存中展示待定内容；若验收要求审计追溯，需在 `0009` 前补一个带 delta 的 change。
