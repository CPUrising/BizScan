# AI 能力边界分析

> 依据：`要求/01.md` 第八章「这一模块必须特别考察 AI 的能力边界」、`README.md` 第 12 节。
> 数据来源：`synthetic-001`（15 例合成，`0014`）、`real-001`（14 张真实，`0015`）、L1 单元测试（`0010`）。
> 口径：只描述实测行为与归因，不给「AI 行/不行」的整体结论；样本 < 30，不宣称统计显著。

## 1. 五类边界的实测结论

| 边界类型 | 合成数据 | 真实名片 | 结论 |
|---|---|---|---|
| 字段歧义（单词多义） | 1/1 正确拒绝（`Apple` 进 `unresolvedLines`） | 无同类样本 | 规则层守住了「不猜」，但没有真正的消歧能力 |
| 人名 / 公司混淆 | 1/1 正确（`Jordan Lee` / `Lee Consulting`） | 3 例误判（c001、c014、c015） | 合成样例过易，真实版式下失效 |
| 多号码分类 | 2/2 正确（`e06` 双手机+座机+传真） | 2 例错误（c001 两号拼接、c015 座机与传真互换） | 依赖标签；无标签或一行多号时失效 |
| 中英混排 | 1/1 正确（`e03`、单行混排） | 1 例部分正确（c007 中英同卡） | 单行可拆，跨行混排未处理 |
| 字段缺失 | `e04`、`e05` 未虚构 | `fabricatedTotal = 0` | **这是唯一被真实数据完整验证的边界** |

## 2. 逐类展开

### 2.1 字段歧义：守住了「不猜」，但没有「判断」

- 证据：`FieldParserTests.testAmbiguousSingleWordStaysUnresolved`、`NoFabricationTests.testUnresolvedContentIsPreserved`。
- 行为：单个英文词（`Apple`）既不是 CJK 姓名也不是 2–3 个首字母大写 token，因此不进入 `name`，也不匹配公司关键词，最终进 `unresolvedLines`。
- 代价：真正只有公司名的名片（如 c013 的 `ROYAL LAW`）会被当成姓名——`ROYAL` 与 `LAW` 都是首字母大写、不含数字，符合 `nameCandidate` 的形态规则。
- 归因：`FieldParser.nameCandidate` 只做**形态**判断（token 数、大小写、是否含数字），不利用版面位置（姓名通常在顶部、字号最大）与语义。
- 结论：这是「拒绝猜测」与「无法判断」的混合体，不能算消歧能力。

### 2.2 人名 / 公司混淆：合成样例过于理想

- 合成侧：`testPersonNameVersusCompanyName` 用 `Jordan Lee` + `Lee Consulting`，公司行命中 `consulting` 关键词，一次通过。
- 真实侧三例失败：

| case | 现象 | 归因 |
|---|---|---|
| c001 | 公司行 `MINPAN NETWORK` 被当成 `name`，人名行 `MIMI ZHOU PEENER` 进 `unresolvedLines` | `NETWORK` 不在 `companyKeywords` 中，公司行先于姓名行出现 |
| c014 | `經理`（职称）被当成 `name` | 姓名行 `許吉米` 在职称行之后；`nameCandidate` 先于 `isJobTitleLine` 之外的分支被命中前，`經理` 已满足 2–4 个 CJK 字符 |
| c015 | `法務助理`（职称）被当成 `name` | 同上；`羅欣怡：東海大學法律素` 含冒号与学历，不满足姓名形态 |

- 关键差异：合成数据的行序是「姓名 → 职称 → 公司」，真实名片常见「公司 → 职称 → 姓名」或「姓名+学历」同行的版式。当前解析按**行序 + 形态**，没有版面坐标参与。
- `OCRObservation` 已携带 `boundingBox`，`FieldParser.parse(observations:)` 只用于排序，未用于字号/位置判定。这是可修的能力缺口，不是模型能力上限。

### 2.3 多号码分类：标签优先，无标签即失效

- 合成侧：`e06` 四行分别带 `Mobile/Tel/Fax` 标签，`PhoneClassifier` 全部正确。
- 真实侧两类错误：

| case | 现象 | 归因 |
|---|---|---|
| c001 | `fax: 021-60230023 021-60230231` 一行两号被拼成 `021-60230023021-60230231`；`tel` 行同理 | 标签行只按「标签 + 单个值」处理，未按空格切分多个号码 |
| c015 | `（04）2223-20121 0972-099-919` 一行含座机与手机，整行进 `unresolvedLines`；后续 `（04）2224-7385` 被归为 `officePhones` 而非 `faxes` | 同上；且传真行缺少 `Fax` 标签时无法区分 |

- 结论：`PhoneClassifier` 的单号码判定正确（`mobiles` 精确率 1.000），失效点是**一行多号的切分**与**无标签时的类型推断**。
- 这正是 `要求/01.md` 第八章「多电话号码：系统必须判断 Mobile / Office / Fax」的考点，当前只部分满足。

### 2.4 中英混排：单行可拆，跨行不合并

- 合成侧：`testMixedSingleLineIsSplitIntoTokens` 用 `朱宏明 Professor Tongji University` 一行，拆成姓名、职称、公司，正确。
- 真实侧：c007 的 `云小印` / `客户经理` / `云印技术（深圳）有限公司` 分三行，全部正确；但同卡还有 `Small Cool Account Manager` 这种英文副标题，进入 `unresolvedLines`。
- 未覆盖：`要求/01.md` 举的 `朱宏明 Professor Tongji University` 若被 OCR 拆成两行（`朱宏明 Professor` + `Tongji University`），当前逻辑不会跨行合并。
- 结论：混排的**单行**场景可用，**跨行**场景未实现。

### 2.5 字段缺失：唯一被真实数据验证的边界

- 合成侧：`e04`（缺 website）、`e05`（缺 email）均未虚构。
- 真实侧：14 张名片 `fabricatedTotal = 0`，包括 6 张 GT 无邮编、5 张 GT 无 website 的样本。
- 机制：`website` 只能由显式域名正则命中；公司名、邮箱域名都不会被推导成 website（`NoFabricationTests` 7 项）。
- 结论：**「不虚构」是本项目唯一在真实数据上成立的 AI 边界**，也是 README 第 11 节唯一的阻断级要求。

## 3. 失败模式的共同结构

三类混淆（人名/公司、职称/姓名、座机/传真）有同一根因：

> 解析器只用「文本形态 + 标签关键词」，不使用「版面位置 + 字号 + 相对顺序」。

因此：

- 版式越接近合成数据（姓名在最上、标签齐全、一行一值），表现越好；
- 版式越接近真实名片（多列、无标签、一行多值、中英混排），失效越集中。

这也解释了为什么合成基线 name 召回 0.933、真实基线只有 0.462——**差距主要来自版式，而不是 OCR 字符识别**（`casesWithOCRTex` 12/14，OCR 本身并非主要瓶颈）。

## 4. 对「AI 能力边界」的结论

| 问题 | 回答 |
|---|---|
| AI 能可靠做什么 | 逐字符识别（12/14 有文本）、显式域名的 website、带标签的单值字段、不虚构 |
| AI 不能可靠做什么 | 无标签号码分类、人名与公司/职称消歧、跨行字段合并、邮编提取（0/6） |
| 人工必须介入什么 | 任何字段的最终确认；尤其姓名、公司、职称、号码类型 |
| 是否可以用「合理猜测」补全 | **不可以**。`要求/01.md` 明确「合理猜测可能恰恰是一种软件错误」，本项目以 `fabricated == 0` 为硬门槛执行 |

## 5. 改进优先级（均需另开 change）

1. `FieldParser` 引入 `boundingBox` 参与判定（字号最大、位置最靠上的行优先作姓名）。
2. 标签行支持一行多值切分（按空格/分隔符）。
3. 无标签号码按区号与位数推断座机/手机；传真需显式标签或关键词。
4. 跨行合并：相邻行若同属地址或同属「姓名+职称」结构，尝试合并。
5. 邮编：从地址尾部提取 4–10 位数字，或识别 `郵遞區號` 等标签。

以上均属产品行为变更，必须走 OpenSpec change 并补回归，不在评估 change 内直接调参。
